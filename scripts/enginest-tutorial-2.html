Chapter 1

Push your code to GitHub

Everything starts here. Vercel needs a place to pull your code from, and that place is GitHub. If you completed Part I, your code is already on GitHub and you can skip to the "Verify it's up to date" section. If you're starting fresh, this chapter walks you through creating a repo and pushing your project for the first time. Take this slow, because the rest of the guide depends on it.

If you haven't pushed yet: create the repo

1
Create a new repository on GitHub

Go to github.com/new. Name it enginest (lowercase, no spaces). Set it to Public or Private, your choice, Vercel works with both. Do not check "Add a README" or "Add .gitignore", we already have those locally. Click "Create repository".

2
Initialize Git locally (if you haven't)

Open a terminal in your project folder. Run git init to start tracking changes. Next.js already created a .gitignore for you, so node_modules and .next will be ignored automatically.

terminal
cd ~/projects/enginest git init git add . git commit -m "Initial commit: Enginest Part I complete"
3
Link your local repo to GitHub

Copy the URL GitHub showed you when you created the repo (looks like https://github.com/YOURNAME/enginest.git). Replace YOURNAME in the commands below with your actual GitHub username.

terminal
git remote add origin https://github.com/YOURNAME/enginest.git git branch -M main git push -u origin main

The -u origin main flag sets the upstream, so future pushes only need git push. Refresh your GitHub repo page, you should see all your project files there. If GitHub asks you to authenticate, use a Personal Access Token instead of your password (GitHub stopped accepting passwords in 2021).

If you already pushed in Part I: verify it's up to date

Run this one command in your project folder:

terminal
git status

You want to see nothing to commit, working tree clean. If you see uncommitted changes, run git add -A && git commit -m "polish before deploy" && git push. You want your local main branch to match what's on GitHub before Vercel imports it.

Pro tip: If git status shows changes you don't recognize, it's probably .next/ build cache that wasn't ignored. Open .gitignore and make sure .next is in there. Then run git rm -r --cached .next to untrack it, commit, and push.
Chapter 2

Sign up for Vercel & link GitHub

Vercel is the hosting platform built by the same team that makes Next.js. It is, by a wide margin, the easiest way to deploy a Next.js app: connect your GitHub repo, click Deploy, and you get a live URL on a global CDN in under two minutes. The free Hobby tier is more than enough for personal projects, portfolios, and prototypes. You only need to pay when you have serious traffic or commercial usage.

1
Sign up at vercel.com

Go to vercel.com and click "Sign Up". Choose "Continue with GitHub", not email. This is critical, because it links your Vercel account to your GitHub account, which is what makes the auto-deploy magic work later.

2
Authorize Vercel to access GitHub

GitHub will ask you to authorize Vercel. Click "Authorize Vercel". You'll be asked which GitHub organizations and repositories Vercel can access. Choose "All repositories" if this is your personal account, or select specific repos if you prefer tighter control.

3
Complete your profile

Vercel asks for your name and a username. Your username becomes part of your default deploy URL (like enginest-YOURNAME.vercel.app). Pick something you don't mind sharing. Choose "Hobby" as your plan, it's free and includes everything we need.

4
Verify the connection

After signup, you'll land on the Vercel dashboard at vercel.com/dashboard. The empty state shows a big "Add New..." button. If you see this, you're ready for the next chapter. Import your repo & first deploy

This is the moment your site goes from "only you can see it" to "anyone in the world can see it". The whole process takes about two minutes. Take your time, read each step, and don't click through anything without understanding what it's asking.

1
Click "Add New..." then "Project"

From the Vercel dashboard, click the "Add New..." dropdown in the top right, then choose "Project". You'll see a list of your GitHub repositories. If you don't see enginest, click "Adjust GitHub App Permissions" and grant Vercel access to that repo.

2
Click "Import" on your enginest repo

Find enginest in the list and click the "Import" button. Vercel shows you a configuration screen with project name, framework preset, root directory, build commands, and install commands.

3
Verify the auto-detected settings

Vercel detects Next.js automatically and fills in everything correctly. You should see: Framework Preset = "Next.js", Build Command = next build, Output Directory = .next, Install Command = npm install. You usually don't change any of these. If something looks wrong, double-check that your package.json has "next" in dependencies.

4
Skip environment variables for now

Vercel shows an "Environment Variables" section. Skip it for now, we'll cover this in the next chapter when we set up the database. Click the blue "Deploy" button at the bottom.

5
Wait for the build to finish

You'll see a live build log scrolling in real time. Vercel runs npm install (about 30 seconds), then next build (about 60 seconds), then uploads the build output to its CDN (about 10 seconds). The whole thing finishes in under 2 minutes for a project this size.

6
Click "Visit" to see your live site

When the build succeeds, Vercel shows confetti and a big "Visit" button. Click it. Your site is now live at a URL like enginest-abc123-YOURNAME.vercel.app. Share this URL with anyone in the world, they can see your site. Copy this URL, you'll use it later when we set environment variables.

Heads up: If your build fails, the most common cause is a TypeScript error or a missing environment variable that your code expects. Click the "Build Logs" tab, scroll to the red error, and read it. terminal

Go back to your Vercel dashboard. Within about 10 seconds you'll see a new deployment start automatically. Wait for it to finish, refresh your live URL, and your change is live. You will never manually deploy again. Every push to main = automatic production deploy. Every push to a branch = automatic preview deploy.

Chapter 4

Environment variables on Vercel

Environment variables (env vars) are how your app knows things that shouldn't be in your code: database passwords, API keys, the production URL, secret tokens. They live in Vercel's encrypted storage and get injected into your app at build time and runtime. Hardcoding secrets in your code is the single biggest beginner mistake in web development. Environment variables are how professionals avoid it.

Local env vars vs production env vars

Locally, you store env vars in a file called .env.local at the root of your project. This file is gitignored (check your .gitignore) so it never ends up on GitHub. In production, you store them in the Vercel dashboard. Both places use the same variable names, but the values can differ (e.g. local dev database vs production database).

Local (.env.local)
Used by npm run dev

Loaded automatically by Next.js when you start the dev server. Never committed to git. Lives at the project root. Format: KEY=value, one per line.

Production (Vercel dashboard)
Used by deployed site

Set in Vercel under Settings → Environment Variables. Encrypted at rest. Scoped to environments (Production, Preview, Development) so you can have different values for each.

Adding your first env var

Let's add one right now so you know the workflow. We'll set NEXT_PUBLIC_SITE_URL, which is a public env var (the NEXT_PUBLIC_ prefix means it's safe to expose to the browser). We'll use it later for canonical URLs and meta tags.

1
Open Settings on Vercel

From your Vercel project dashboard, click the "Settings" tab at the top, then "Environment Variables" in the left sidebar.

2
Add the variable

In the "Key" field type NEXT_PUBLIC_SITE_URL. In the "Value" field paste your live Vercel URL (like https://enginest-abc123-YOURNAME.vercel.app, no trailing slash). Check all three environments: Production, Preview, Development. Click "Save".

3
Mirror it locally

Create a file at the root of your project called .env.local and add the same variable pointing to localhost:

.env.local
NEXT_PUBLIC_SITE_URL=http://localhost:3000
4
Use it in your code

Anywhere in your app, you can now reference process.env.NEXT_PUBLIC_SITE_URL and it'll resolve to the right value in both environments. Try it in a meta tag:

src/app/layout.tsx
<meta property="og:url" content={process.env.NEXT_PUBLIC_SITE_URL} />
5
Redeploy to pick up the new env var

Vercel only reads env vars at build time. Adding a new one doesn't affect existing deployments. Go to "Deployments" tab, click the three dots next to your latest deploy, choose "Redeploy". Your site now has access to NEXT_PUBLIC_SITE_URL.

Critical: Any variable prefixed with NEXT_PUBLIC_ is exposed to the browser. Never prefix a secret with this. Database passwords, API secrets, and auth tokens must stay non-prefixed so they only exist on the server side.
Chapter 5

Next.js App Router — how pages work

Now we shift from deployment to features. The Next.js App Router is the modern routing system that ships with Next.js 13+. It uses a file-based routing convention: the files you create in src/app/ literally become the URLs of your site. No route configuration files, no router.js, no XML. Just files and folders. This is one of the most elegant parts of Next.js and once it clicks, you'll never want to go back to manual routing.

The core conventions

Three file names have special meaning in the App Router. Memorize these:

  • page.tsx — Defines the UI for a URL. If a folder has a page.tsx, that folder's path is routable. If it doesn't, the folder is just organizational.
  • layout.tsx — Wraps all pages in that folder and below. Use it for shared chrome like navbars, footers, sidebars. Layouts persist across page navigations (no full page reload).
  • loading.tsx — Shows a spinner or skeleton while the page is loading. Optional but excellent for perceived performance.

Your current file structure

After Part I, your src/app/ folder looks roughly like this:

src/app/ ├── layout.tsx # root layout, wraps everything ├── page.tsx # homepage, URL: / ├── globals.css ├── solve-them/ │ └── page.tsx # URL: /solve-them ├── innovation-engine/ │ └── page.tsx # URL: /innovation-engine ├── dashboard/ │ ├── layout.tsx # dashboard shell with sidebar │ ├── page.tsx # URL: /dashboard │ └── innovation-engine/ │ └── page.tsx # URL: /dashboard/innovation-engine └── auth/ ├── login/ │ └── page.tsx # URL: /auth/login └── signup/ └── page.tsx # URL: /auth/signup

See the pattern? Folders = URL segments. page.tsx inside a folder = that URL is routable. Nested folders = nested URLs. No config needed.

Creating a new page in 30 seconds

Let's add an "About" page. Create a new folder called about inside src/app/, and a file called page.tsx inside it. That's it. The URL /about now works.

src/app/about/page.tsx
export default function AboutPage() { return ( <main className="min-h-screen bg-white px-6 py-20"> <div className="max-w-3xl mx-auto"> <h1 className="text-4xl font-bold text-[#0F1B3D]">About Enginest</h1> <p className="mt-4 text-lg text-slate-600"> Enginest curates real-world engineering problems and matches them to your skills with AI. </p> </div> </main> ); }

Save the file. Open http://localhost:3000/about in your browser. The page is live, with hot reload, no restart needed. Add a link to it from your navbar by editing src/components/PublicNavbar.tsx and adding <Link href="/about">About</Link> to the nav links.

Add a new page at /contact with a centered layout, dark navy background (#0F1B3D), a headline "Get in touch", a subheadline, and a simple contact form with name, email, and message fields. Use Tailwind CSS and the Next.js App Router. Make the form submit to a placeholder for now, we'll wire it up to a Server Action later.

The AI will generate src/app/contact/page.tsx. Save it, and /contact is live. Notice you didn't touch any routing config. This is the power of file-based routing.

Chapter 6

Static, dynamic, and nested routes

File-based routing handles three cases: static routes (like /about), dynamic routes (like /problems/[slug] where slug varies), and nested routes (like /dashboard/analytics/weekly). All three follow the same folder-based convention, but dynamic routes use a special bracket syntax that you need to understand.

Static routes — the simple case

A folder named about with a page.tsx becomes the URL /about. That's static routing, covered in the last chapter. The URL is fixed, the page is fixed, the content is whatever you put in the JSX. Easy.

Dynamic routes — the bracket syntax

What if you want a page per problem, like /problems/energy-storage, /problems/clean-water, /problems/carbon-capture, all powered by the same component but with different data? That's a dynamic route. You create a folder with square brackets around a parameter name: [slug]. The bracket name becomes the parameter you read in your code.

src/app/problems/ └── [slug]/ └── page.tsx # URL: /problems/energy-storage, /problems/clean-water, etc.

Inside the page component, you read the slug from the params prop and use it to fetch the right data. In Next.js 15+, params is a Promise that you await:

src/app/problems/[slug]/page.tsx
export default async function ProblemPage({ params, }: { params: Promise<{ slug: string }>; }) { const { slug } = await params; // ...look up the problem with this slug, render it... return ( <main> <h1>Problem: {slug}</h1> </main> ); }

Pre-generating dynamic routes with generateStaticParams

If your problems come from a known list (a TypeScript file, a CMS, a database), you can tell Next.js to pre-render all of them at build time. This is faster for users and better for SEO. You do this by exporting a generateStaticParams function from your dynamic page:

src/app/problems/[slug]/page.tsx
import { problems } from "@/lib/solve-them/problems"; export function generateStaticParams() { return problems.map((p) => ({ slug: p.slug })); } export default async function ProblemPage({ params, }: { params: Promise<{ slug: string }>; }) { const { slug } = await params; const problem = problems.find((p) => p.slug === slug); if (!problem) return <div>Not found</div>; return <h1>{problem.title}</h1>; }

At build time, Next.js calls generateStaticParams, gets the list of slugs, and pre-renders a page for each one. The result is a folder of static HTML files, one per problem, served from Vercel's CDN at zero compute cost.

Nested routes — just more folders

Want /dashboard/analytics/weekly? Just create folders: src/app/dashboard/analytics/weekly/page.tsx. The depth is unlimited, but practically you'll rarely go more than 3 levels deep. Each folder can have its own layout.tsx if you want different chrome for different sections.

Pattern: If two pages share chrome (navbar, sidebar, footer), wrap them in a layout. If a page is unique and doesn't share chrome, just use a page. Layouts are powerful but don't overuse them, every layout adds a React boundary that affects performance.
Chapter 7

Server Components vs Client Components

This is the most important mental model in modern Next.js, and it confuses every beginner. Get this right and everything else clicks. Get it wrong and you'll see errors like "useState is not a function" or "useSearchParams should be wrapped in a Suspense boundary" and have no idea why.

The default: Server Components

Every component in the src/app/ directory is a Server Component by default. Server Components run on the server (in Node.js, not in the browser), render to HTML, and ship that HTML to the browser. They have zero JavaScript footprint in the bundle. They can directly access databases, read files, use async/await for data fetching, and use secrets from process.env safely. They cannot use React hooks like useState, useEffect, or useRouter, because those require client-side JavaScript.

The opt-in: Client Components

When you need interactivity (a button that toggles state, a form that validates input, an animation that responds to scroll), you need a Client Component. You opt in by adding "use client" as the very first line of the file. Client Components ship JavaScript to the browser and can use hooks, events, and browser APIs. They cannot directly access databases or use secret env vars. They run in the user's browser, where secrets would be exposed.

Server Component (default)
Runs on the server
  • Can fetch data from DB directly
  • Can use async/await
  • Can use secret env vars
  • Zero JS shipped to browser
  • Cannot use useState, useEffect
  • Cannot use onClick, onChange
  • Best for: data-heavy pages, layouts, marketing
Client Component ("use client")
Runs in the browser
  • Can use useState, useEffect, useRouter
  • Can use onClick, onChange, onSubmit
  • Can use browser APIs (localStorage, etc.)
  • Ships JS to browser (bundle cost)
  • Cannot directly access DB
  • Cannot use secret env vars
  • Best for: forms, interactive widgets, animations

The pattern: Server Component as the page, Client Component for interactive bits

The cleanest pattern is to keep your page.tsx as a Server Component (for data fetching and SEO), and split out interactive parts into Client Components that you import. The Server Component fetches data, passes it as props to the Client Component, and the Client Component handles interactivity. This gives you the best of both worlds: server-side data access with client-side interactivity.

src/app/contact/page.tsx (Server Component)
import ContactForm from "./ContactForm"; export default function ContactPage() { return ( <main> <h1>Get in touch</h1> <ContactForm /> </main> ); }
src/app/contact/ContactForm.tsx (Client Component)
"use client"; import { useState } from "react"; export default function ContactForm() { const [submitted, setSubmitted] = useState(false); return ( <form onSubmit={() => setSubmitted(true)}> {/* form fields */} {submitted && <p>Thanks!</p>} </form> ); }
Rule of thumb: Start with Server Components. Only add "use client" when you actually need a hook or an event handler. The fewer Client Components you have, the smaller your JS bundle and the faster your site.
Chapter 8

Why a database & picking Prisma + Postgres

Up to now, your site's data lives in TypeScript files. That works for fixed content like your problem catalog, but it breaks down the moment you want users to create data: accounts, comments, submissions, votes, saved items. For that, you need a database. A database is just a structured storage system that lets your app store, query, and update data without you manually editing files.

The options (and why we picked this stack)

There are many databases. For a Next.js project deployed on Vercel, the most natural choice is Vercel Postgres (a managed PostgreSQL instance that lives in your Vercel dashboard, billed on the same invoice, connected to your app with a single env var). To talk to it from your Next.js code, we'll use Prisma, an ORM that gives you a TypeScript-safe query API. This stack (Next.js + Vercel Postgres + Prisma) is the most popular production database setup in the Next.js ecosystem.

Why Postgres
Relational, mature, fast
  • Free tier on Vercel: 60 hours compute, 256MB storage
  • Standard SQL, easy to learn
  • Handles relations (users → posts → comments)
  • ACID transactions for data integrity
  • Works with any hosting provider, not locked in
Why Prisma
Type-safe ORM
  • Schema-first: define models in a .prisma file
  • Auto-generates a TypeScript client
  • Autocomplete on every query, no typos
  • Handles migrations safely
  • Works with Postgres, MySQL, SQLite, MongoDB

What you'll build in the next chapters

We're going to add a "Saved Problems" feature. Users will be able to save problems they care about, and the saved list will persist across sessions. This requires three things: a database table to store saved problems, a Prisma schema to define that table, and Server Actions to add and remove items. By the end of Chapter 12, your site will have a real database with real user-created data.

Heads up: Vercel Postgres free tier is generous for personal projects (256MB storage, 60 compute hours per month). If you exceed it, Vercel emails you before charging. For learning, the free tier is more than enough.
Chapter 9

Install Prisma & write your schema

Prisma is a Node.js ORM (Object-Relational Mapper). You describe your database tables in a single schema.prisma file, run a command, and Prisma generates a fully type-safe client that you import in your code. No raw SQL strings, no manual type definitions, just clean TypeScript queries with autocomplete.

Install Prisma

Run this in your project folder. It installs the Prisma CLI as a dev dependency and the Prisma Client as a runtime dependency:

terminal
npm install prisma --save-dev npm install @prisma/client npx prisma init

The npx prisma init command creates two things: a prisma/schema.prisma file (where you'll define your tables) and a .env file (where the database connection string lives). Next.js will complain about .env, you should rename it to .env.local to follow Next.js convention.

Important: Delete the example DATABASE_URL line that Prisma put in .env.local and replace it with your actual Vercel Postgres connection string (we'll get this in the next chapter). For now, leave it as a placeholder.

Write your schema

Open prisma/schema.prisma and replace the example model with these two models. The Problem model represents one engineering problem from your catalog. The SavedProblem model represents a user saving a problem to their list. We'll keep user auth simple for this guide, just a session ID stored in a cookie.

prisma/schema.prisma
// This is your Prisma schema file, // learn more: https://pris.ly/d/prisma-schema generator client { provider = "prisma-client-js" } datasource db { provider = "postgresql" url = env("DATABASE_URL") } model Problem { id String @id @default(cuid()) slug String @unique title String category String createdAt DateTime @default(now()) updatedAt DateTime @updatedAt savedBy SavedProblem[] @@map("problems") } model SavedProblem { id String @id @default(cuid()) sessionId String problemId String createdAt DateTime @default(now()) problem Problem @relation(fields: [problemId], references: [id], onDelete: Cascade) @@unique([sessionId, problemId]) @@map("saved_problems") }

Reading the schema

Let's break down what's happening here:

  • generator client — tells Prisma to generate the JS client we'll import in our code.
  • datasource db — tells Prisma we're using Postgres, and where to find the connection string (in DATABASE_URL env var).
  • model Problem — a table called problems (the @@map renames it). Each row has an id (auto-generated cuid), a unique slug, a title, a category, and timestamps.
  • model SavedProblem — a join table. Each row says "this session saved this problem". The @@unique constraint prevents duplicate saves. The problem field is a relation, so you can do savedProblem.problem.title in your code.
  • onDelete: Cascade — if a Problem is deleted, all SavedProblem rows pointing to it are deleted too. Prevents orphan rows.

I have a Prisma schema with a Problem model and a SavedProblem model. Generate the schema file content for me, including the generator block, datasource block, both models with proper relations, and the @@map and @@unique directives. Use PostgreSQL. Use cuid() for IDs. Include createdAt and updatedAt on Problem, createdAt on SavedProblem. SavedProblem should have a unique constraint on [sessionId, problemId].

The AI will produce exactly the schema above. Save it to prisma/schema.prisma. We're not running the migration yet, that comes after we set up the actual database.

Chapter 10

Provision Vercel Postgres & wire connection

Now we create the actual database. Vercel Postgres is a managed PostgreSQL instance that lives in your Vercel project. It's billed on the same invoice as your Vercel subscription, the free tier includes 256MB storage which is plenty for learning. Provisioning takes about 30 seconds.

1
Open the Storage tab

From your Vercel project dashboard, click the "Storage" tab at the top. You'll see an empty state with options for Postgres, KV (Redis), Blob (file storage), and Edge Config. We want Postgres.

2
Create a Postgres database

Click "Create Database" → choose "Postgres" → choose "Hobby" (free tier). Name it enginest-db. Click "Create". Vercel provisions the database in about 30 seconds.

3
Connect it to your project

After creation, Vercel shows you a "Connect to Project" dropdown. Select your enginest project. Vercel automatically adds the POSTGRES_URL, POSTGRES_PRISMA_URL, POSTGRES_URL_NON_POOLING, and a few other env vars to your project, in all three environments (Production, Preview, Development).

4
Get your local connection string

On the database page, click ".env.local" tab. Vercel shows you a snippet with all the env vars and their values. Copy this entire snippet.

5
Paste into your local .env.local

Open your local .env.local file (at the project root) and paste the snippet at the bottom. Prisma specifically wants the POSTGRES_PRISMA_URL (pooled, for queries) or POSTGRES_URL_NON_POOLING (for migrations). Add this line at the bottom of .env.local:

.env.local (append)
DATABASE_URL="postgres://..." # use the value of POSTGRES_PRISMA_URL here
Two connection strings, two purposes: Use the pooled URL (POSTGRES_PRISMA_URL) as your DATABASE_URL for normal queries. Use the non-pooled URL (POSTGRES_URL_NON_POOLING) for migrations, since Prisma migrate needs a direct connection. If you only set DATABASE_URL, use the pooled one, queries will work fine, migrations will warn but still work.
6
Pull the env vars to local automatically (alternative)

If you'd rather not copy-paste, install the Vercel CLI and pull env vars with one command:

terminal
npm install -g vercel vercel login vercel link # links your local project to your Vercel project vercel env pull .env.local # downloads all env vars from Vercel

This overwrites your .env.local with all the env vars set on Vercel, including the Postgres connection strings. Useful when you have many env vars or work across machines.

Run your first migration

Now that Prisma knows where the database is, push your schema to create the actual tables:

terminal
npx prisma db push

This synchronizes your schema.prisma with the database, creating the problems and saved_problems tables. Open your Vercel Postgres dashboard and click "Data Browser", you'll see the empty tables there. You've just connected a real database to your app.

Chapter 11

Connect pages to the database

Now we generate the Prisma Client (the typed query API) and use it from a Server Component to read data. This is where the magic happens: your React components can directly query the database, no API endpoint required, no fetch boilerplate.

Generate the Prisma Client

terminal
npx prisma generate

This reads your schema.prisma and generates a TypeScript client in node_modules/.prisma/client. You'll re-run this command every time you change your schema. The client gives you methods like prisma.problem.findMany() and prisma.savedProblem.create() with full type safety and autocomplete.

Create a Prisma Client singleton

In development, Next.js hot-reloads your modules, which can spawn dozens of Prisma Client instances and exhaust your database connections. The fix is a singleton pattern: a small file that creates one client and reuses it. Create this file:

src/lib/prisma.ts
import { PrismaClient } from "@prisma/client"; const globalForPrisma = globalThis as unknown as { prisma: PrismaClient | undefined; }; export const prisma = globalForPrisma.prisma ?? new PrismaClient({ log: ["query"], }); if (process.env.NODE_ENV !== "production") globalForPrisma.prisma = prisma;

Now any file that imports { prisma } from @/lib/prisma gets the same instance. In production, a fresh client is created per cold start. This is the official Prisma + Next.js pattern, copy it verbatim.

Seed some data

Before we can read data, we need some. Let's seed the database with a few problems. Create a quick seed script:

scripts/seed.ts
import { prisma } from "../src/lib/prisma"; async function main() { await prisma.problem.createMany({ data: [ { slug: "energy-storage", title: "Grid-Scale Energy Storage", category: "Energy" }, { slug: "clean-water", title: "Affordable Clean Water", category: "Water" }, { slug: "carbon-capture", title: "Direct Air Carbon Capture", category: "Climate" }, ], }); console.log("Seeded 3 problems"); } main() .catch((e) => { console.error(e); process.exit(1); }) .finally(async () => { await prisma.$disconnect(); });

npx tsx scripts/seed.ts

If you don't have tsx installed, run npm install -D tsx first. This executes the TypeScript file directly. You should see "Seeded 3 problems" printed. Check your Vercel Postgres Data Browser, the problems table now has 3 rows.

Read from a Server Component

Now the moment of truth: read these problems from a page. Create a new page at src/app/problems/page.tsx that lists all problems:

src/app/problems/page.tsx
import { prisma } from "@/lib/prisma"; export default async function ProblemsPage() { const problems = await prisma.problem.findMany({ orderBy: { createdAt: "desc" }, }); return ( <main className="min-h-screen bg-white px-6 py-20"> <div className="max-w-4xl mx-auto"> <h1 className="text-4xl font-bold text-[#0F1B3D]">Problems</h1> <ul className="mt-8 space-y-4"> {problems.map((p) => ( <li key={p.id} className="border border-slate-200 rounded-lg p-4"> <a href={`/problems/${p.slug}`} className="text-xl font-semibold text-[#0F1B3D]"> {p.title} </a> <p className="text-sm text-slate-500 mt-1">{p.category}</p> </li> ))} </ul> </div> </main> ); }

Save the file. Visit http://localhost:3000/problems. You should see your three seeded problems listed. You just queried a database from a React component. No API endpoint, no fetch, no JSON parsing, no loading state, no error handling boilerplate. The await is real (the page renders on the server, waits for the query, ships the HTML).

Why this is huge: In old Next.js (Pages Router), you'd write a separate API route, fetch from the client, parse JSON, handle loading and error states. With the App Router and Prisma, it's just await prisma.problem.findMany() in your component. The complexity drops by 80%.
Chapter 12

Server Actions — save data from forms

Reading data is half the picture. The other half is writing it. Server Actions are Next.js's answer to "I want a form that saves to my database without writing an API endpoint". You write an async function marked with "use server", attach it to a form's action prop, and Next.js handles the rest: serialization, network call, and re-rendering the page with fresh data.

Create a Server Action

Create a new file src/app/problems/actions.ts:

src/app/problems/actions.ts
"use server"; import { prisma } from "@/lib/prisma"; import { revalidatePath } from "next/cache"; export async function addProblem(formData: FormData) { const slug = formData.get("slug") as string; const title = formData.get("title") as string; const category = formData.get("category") as string; await prisma.problem.create({ data: { slug, title, category }, }); revalidatePath("/problems"); }

Three things happen here: (1) "use server" at the top marks this file as containing only server-side functions, Next.js will never ship this code to the browser. (2) We read the form fields by their name attributes. (3) revalidatePath tells Next.js to purge the cache for /problems so the new problem shows up immediately on the next render.

Wire the action to a form

Update your problems/page.tsx to include a form that calls the action:

src/app/problems/page.tsx (updated)
import { prisma } from "@/lib/prisma"; import { addProblem } from "./actions"; export default async function ProblemsPage() { const problems = await prisma.problem.findMany({ orderBy: { createdAt: "desc" }, }); return ( <main className="min-h-screen bg-white px-6 py-20"> <div className="max-w-4xl mx-auto"> <h1 className="text-4xl font-bold text-[#0F1B3D]">Problems</h1> {/* The form */} <form action={addProblem} className="mt-8 space-y-3"> <input name="slug" placeholder="slug" required className="block w-full border rounded p-2" /> <input name="title" placeholder="title" required className="block w-full border rounded p-2" /> <input name="category" placeholder="category" required className="block w-full border rounded p-2" /> <button type="submit" className="bg-[#0F1B3D] text-white px-4 py-2 rounded"> Add problem </button> </form> {/* The list */} <ul className="mt-8 space-y-4"> {problems.map((p) => ( <li key={p.id} className="border border-slate-200 rounded-lg p-4"> <a href={`/problems/${p.slug}`} className="text-xl font-semibold text-[#0F1B3D]"> {p.title} </a> <p className="text-sm text-slate-500 mt-1">{p.category}</p> </li> ))} </ul> </div> </main> ); }

Save it. Open http://localhost:3000/problems. Type a slug, title, and category into the form, hit "Add problem". The page reloads and your new problem appears at the top of the list. Behind the scenes: the form submitted to your Server Action, the action inserted a row into the database, revalidatePath purged the cache, and the page re-rendered with fresh data. You wrote zero API code.

Chapter 13

Deploy database changes to production

Your local dev database has 3 seeded problems and a working form. But your production Vercel deployment doesn't know any of this yet. When Vercel builds your project, it runs npm run build, which compiles your code, but it does not automatically run Prisma migrations. You have to wire that up. Here's how.

Step 1: Create a real migration

Up to now we used prisma db push, which is fine for prototyping but doesn't create migration files. For production, you want migration files committed to your repo so every deploy applies the same schema changes deterministically. Run:

terminal
npx prisma migrate dev --name init

This does three things: (1) creates a prisma/migrations/ folder with a timestamped SQL migration, (2) applies it to your dev database, (3) regenerates the Prisma Client. Commit the migrations/ folder to git. From now on, every schema change starts with prisma migrate dev --name something.

Step 2: Add a postinstall hook

When Vercel builds your app, it runs npm install first. After install, you want Prisma to (1) regenerate the client and (2) apply pending migrations to the production database. Add this to your package.json:

package.json (scripts section)
"scripts": { "dev": "next dev", "build": "next build", "start": "next start", "lint": "next lint", "postinstall": "prisma generate" }

The postinstall hook runs automatically after npm install on Vercel, regenerating the Prisma Client so it's available during next build. This is essential, without it, your build fails with "PrismaClient is not defined".

Step 3: Run migrations on deploy

For running migrations on production, you have two options. The simpler one for small projects is to add prisma migrate deploy to your build command:

package.json (scripts section)
"scripts": { "dev": "next dev", "build": "prisma migrate deploy && next build", "start": "next start", "lint": "next lint", "postinstall": "prisma generate" }

Now every Vercel build runs prisma migrate deploy first (applies any pending migrations to the production DB), then next build. This is the standard pattern for Next.js + Prisma on Vercel.

For larger teams: The "migrate on build" pattern is fine for solo projects. For team projects with multiple environments, you typically run prisma migrate deploy as a separate step in CI/CD before deploying, so a bad migration doesn't take down production. For learning, the build-step pattern is perfectly fine.

4
Commit and push

Commit your package.json changes, the new prisma/migrations/ folder, and the src/lib/prisma.ts file. Push to GitHub. Vercel auto-deploys, runs the migration against production, and your live site now has a working database.

terminal
git add -A git commit -m "feat: prisma + postgres, problems CRUD with server actions" git push

Watch your Vercel deployment logs. You should see prisma migrate deploy output "Applied 1 migration", followed by next build succeeding. Visit your live URL /problems, the page renders (empty, since prod DB is empty). Submit the form, your new problem is saved to the production database. You've deployed a full-stack app with a real database.

Chapter 14

Common pitfalls & fixes

Real projects hit real problems. Here are six actual issues you're likely to hit during this guide, with the symptoms, causes, and fixes. When you hit them, refer back here.

Problem 01
Build fails on Vercel: "PrismaClient is not defined"

Your build runs next build but Prisma Client wasn't generated. The error appears in the build log as a TypeScript error or a runtime error during static generation.

Fix

Add "postinstall": "prisma generate" to your package.json scripts. This runs after npm install on Vercel, generating the client before the build. Alternatively, change your build command to "build": "prisma generate && next build".

Problem 02
"Too many connections" errors in dev

Next.js hot-reloads your modules, and each reload creates a new Prisma Client. After 20-30 saves, you've exhausted Postgres's connection limit. The error shows up as Error: remaining connection slots are reserved for non-replication superuser connections.

Fix

Use the singleton pattern shown in Chapter 11. The key line is globalForPrisma.prisma ??= new PrismaClient(), which reuses the same client across hot reloads. Never call new PrismaClient() directly inside a component or page file.

Problem 03
"useSearchParams should be wrapped in a suspense boundary"

You used useSearchParams (or any hook that reads the URL) in a Client Component during static build. Next.js needs to know what to render before the URL is known, so it requires a Suspense wrapper.

Fix

Wrap the component using useSearchParams in a <Suspense fallback={...}> tag. Or use export const dynamic = "force-dynamic" at the top of the page to opt out of static rendering. Or refactor to read params from the Server Component's params prop instead.

Problem 04
Form submission shows 405 Method Not Allowed

Your Server Action isn't being recognized. The form submits to a URL that doesn't exist. Usually caused by forgetting "use server" at the top of actions.ts, or by importing the action from a non-server file.

Fix

Make sure actions.ts starts with "use server". Make sure you're importing the action as a value (import { addProblem } from "./actions"), not as a default export. Make sure the form's action prop is set to the function reference, not a string URL.

Problem 05
Env var works locally but not on Vercel

Locally your site reads process.env.DATABASE_URL fine. On Vercel, it's undefined. Usually caused by (1) only adding the env var to one environment (e.g. Production but not Preview), or (2) naming mismatch.

Fix

Go to Vercel → Settings → Environment Variables. Check that the variable is checked for all three environments (Production, Preview, Development). Check the name matches exactly, case-sensitive. After adding, you must redeploy (env vars are read at build time).

Problem 06
Prisma migrate fails on Vercel build

The build log shows prisma migrate deploy failing with "database does not exist" or "authentication failed". The production DATABASE_URL is either missing or pointing to the wrong database.

Fix

Verify your Vercel project is connected to your Postgres instance (Storage tab → click the database → "Connect to Project"). Verify DATABASE_URL is set in Vercel env vars (it should be auto-set when you connect). For migrations, Prisma needs the non-pooled URL: set DIRECT_URL to POSTGRES_URL_NON_POOLING and add directUrl = env("DIRECT_URL") to your schema's datasource block.
